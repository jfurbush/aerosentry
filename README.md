# AeroSentry

Predictive maintenance dashboard that estimates Remaining Useful Life (RUL), in operating cycles, for turbofan engines. It uses the NASA CMAPSS FD001 dataset, which is simulated data. It is not a failure analysis tool and does not produce fixed maintenance intervals. It gives a per-engine RUL estimate and a sensor trend so a planner can decide when to schedule maintenance.

## Rebuild the database and model

The database and model are generated files and are not committed. The raw FD001 files are in `data/raw/`. To build them:

```
python -m pipeline.load_db     # writes data/aerosentry.db
python -m pipeline.train       # writes models/rul_model.joblib and models/metrics.json
```

Training uses a fixed random seed.

## Run the service

Build the database and model first (see above), then:

```
uvicorn app.main:app --reload
```

- **Web Dashboard**: Open http://localhost:8000/ in your browser. The home page lists the engines. Each engine page shows the predicted RUL in cycles, a chart of the model's predicted RUL at every recorded cycle, and one sensor at a time, chosen from a list, plotted over the operating cycles with a 10-cycle moving average. The RUL is capped at 125 cycles, so a value near 125 means about 125 cycles or more. The model's error was measured only at the last recorded cycle of each test engine, so the earlier points on the RUL chart are predictions with no measured error. A sensor that never changes for the engine is marked as constant. Sensor names and units are from Table 2 of Saxena et al. (see Data and attribution). An unknown engine, a bad engine ID or an unavailable database or model shows an error page with a link back to the list.
  The dashboard needs no internet access: its styles and the Plotly charting library are served by the app itself (`app/static/`, see `app/static/vendor/README.md`).
- **API Docs**: Interactive Swagger documentation is available at http://localhost:8000/docs. This page is generated by FastAPI and loads its files from a public CDN, so it needs internet access. The dashboard and the API do not.

API endpoints:

- `GET /health` returns `{"status": "ok"}` while the service is running. It is a liveness check only and does not touch the model or database.
- `GET /engines` returns a list of `{"engine_id", "n_cycles"}` for each engine in the database.
- `POST /predict` with `{"engine_id": 1}` returns `engine_id`, `cycle` (the engine's latest recorded cycle) and `predicted_rul` in cycles. The model was trained on RUL capped at 125, so a value near 125 means "at least about 125".

Errors are always `{"detail": "..."}`:

- 404: unknown engine ID.
- 422: malformed request, including a non-integer, zero, negative, or missing `engine_id`.
- 503: the database or model file is unavailable.
- 500: the model and database do not match.

## Docker

Build (trains the model during the build, from `data/raw/`):

```
docker build -t aerosentry:latest .
```

Run:

```
docker run --rm -p 8000:8000 aerosentry:latest
```

The container runs as a non-root user.

Check a running container (needs bash and curl; on Windows use Git Bash or WSL). Run it from the same commit the image was built from:

```
bash scripts/smoke_test.sh http://localhost:8000
```

It calls `/health`, `/engines`, `/predict`, a missing engine, the dashboard pages and `/static`, and compares the served Plotly file with the checksum recorded in `app/static/vendor/README.md`.

## CI/CD and deployment

- `ci.yml` runs on every push and pull request. Job `test-and-analyze` runs ruff, mypy, bandit (`-lll`) and pytest with a coverage minimum of 80%, and uploads the reports as the artifact `ci-reports`. Job `docker-smoke-test` builds the image, starts the container, runs `scripts/smoke_test.sh` against it and uploads the image size, the smoke test output and the container log as the artifact `docker-reports`. Nothing is pushed.
- `cd.yml` builds the Docker image and pushes it to GitHub Container Registry as `ghcr.io/jfurbush/aerosentry`, tagged with the commit SHA (`sha-` and the first 7 characters) and `latest`. It is set to start after CI has passed on a push to `main`, and it can also be started by hand from the Actions tab or with `gh workflow run CD --ref main`. A manual run on 2026-11-09 pushed the image, and the package is public.

The published image can be pulled with:

```
docker pull ghcr.io/jfurbush/aerosentry:latest
docker run --rm -p 8000:8000 ghcr.io/jfurbush/aerosentry:latest
```

A live hosted instance is not part of the core scope.
